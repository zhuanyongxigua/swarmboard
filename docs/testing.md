# 测试分层

目标是分别证明规则、存储、协议和界面行为。源码里有测试、CI 执行了测试、以及真实客户端验收是不同证据；当前实际结果见 [verification.md](verification.md)。

| 层 | 命令 | 要证明的行为 |
| --- | --- | --- |
| 领域/单元 | `npm run test:unit` | 输入验证、状态、归属、版本冲突、资源共同使用 |
| SQLite 集成 | `npm run test:integration` | 真实事务、迁移、失败回滚、重开持久化、事件追加约束 |
| HTTP 黑盒 | `npm run test:api` | 实际启动的服务、路由、错误状态、认证、跨客户端变化 |
| MCP 协议 | `npm run test:mcp` | 官方 SDK 客户端的初始化、工具发现与调用、UI 资源、错误和增量游标 |
| 桌面插件打包 | `npm run package:desktop` | 构建自包含服务、界面、manifest 和 skill；成功打包本身不证明客户端已安装 |
| 桌面便携包协议 | `npm run test:desktop` | 先打包，再从 ZIP 解压到新临时目录，用官方 SDK 启动真实 stdio 子进程，验证工具、资源及持久化 |
| 浏览器 | `npm run test:e2e` | 真实服务和数据库上的任务分列、拖动及键盘改状态、双会话编辑冲突、资源声明与刷新持久化 |
| 完整检查 | `npm run check` | lint、类型、服务构建、桌面打包、覆盖率和浏览器测试串联 |

`npm run test:coverage` 执行全部 Vitest 套件并检查核心服务覆盖率门槛。会话适配器和事件运行时另有组件门槛：分支均至少 70%，行分别至少 95% / 88%，避免全仓平均值掩盖组件退步。真实子进程故障路径不计入父进程 V8 覆盖率，行为断言仍须独立通过。覆盖率不能代替协议与浏览器行为验证；前端主要通过浏览器路径验收。CI 应通过 `npm ci` 使用锁文件，并安装浏览器后执行同一完整检查。

直接运行 `test:mcp`、`test:coverage` 或 `test` 前，需要先执行 `npm run package:desktop`，因为桌面套件验证实际 ZIP 而不是源码模拟物。`test:desktop` 和 `check` 已自动包含打包步骤。`src/index.ts` 与 `src/stdio.ts` 是真实子进程入口，不计入进程内 V8 覆盖率；它们的启动、协议和退出行为由黑盒测试单独证明。

所有数据均为合成数据，使用隔离数据库和临时端口；测试不访问真实开发机，也不调用模型。并发测试验证版本与原子事件，不能据此声称实现了真实机器隔离。XSS、非法输入和过期写入属于可观察的边界测试。

浏览器回归还检查无类型表单的新资源创建、旧资源编辑不覆盖已有类型与能力、两条共享使用声明分别释放，以及只读共享记录的文本转义。两个独立浏览器会话同时编辑同一任务时，过期写入必须被拒绝，草稿保留，用户显式载入最新内容后才能再保存。

本地模拟宿主用来验证 MCP Apps 桥接、iframe 沙箱中的表单提交以及嵌入时不访问 HTTP 开发接口，是受控协议测试；它不等同于 ChatGPT 已安装、真实宿主权限批准或插件商店审核。真实多 Agent 的产出质量与成本需要单独实验，不属于确定性回归测试的结论。

桌面套件通过官方 SDK 启动真实子进程，验证工具和 UI 资源。它从 ZIP 解压到新临时目录，使用隔离数据库、与源码无关的 cwd、没有 node_modules 的目录启动，检查 `${PLUGIN_ROOT}`、重启持久化、双进程首次初始化与认领竞争。macOS 临时路径符号链接和 SQLite WAL 初始化锁均包含实际失败后修复的回归证据。MCP 元数据存在及官方 CLI 安装成功不代表实际客户端已显示侧边栏，后者必须在真实桌面宿主验收。

原生讨论回归通过模拟桌面宿主检查实际 `ui/message` 出站信封，确认 `target: active`、`send: false` 扩展元数据没有被 SDK 基础 schema 丢弃。测试覆盖已有草稿保留、仅显式点击触发、选中任务只引用已保存版本、宿主不支持或拒绝时不降级为立即发送，以及完整数据库状态无变化。移动端即使声明消息能力也禁用此入口。`planning_partner` 通过官方 MCP 客户端发现和读取，检查讨论与摘要不构成写入授权，读取 prompt 后数据库保持不变。

这些测试不调用模型，不证明模型一定遵循规划约定，也不证明真实 ChatGPT 桌面版的面板位置、模型菜单、权限菜单或草稿交互；这些需要真实宿主验收。

双语文档截图由实际界面（英文 `?lang=en`、中文 `?lang=zh-CN`）和对应语言的隔离示例数据生成。截图脚本对英文视图检查可见文字无中文、文档语言一致且无横向溢出。浏览器回归验证英文表单真实保存、状态更新、切换中文后原始用户输入保持不变；便携包回归检查两份 README 各自引用三张对应语言的图片，解压后文件存在。

桌面启动回归还覆盖 GUI 精简 PATH：从干净 ZIP 解压，在仅有 `sh`、没有 Node 或其他外部命令的 PATH 下，通过带空格的隔离 NVM 路径发现实际运行时，完成真实 MCP 初始化、工具发现与 HTML 读取；无效显式运行时必须以 127 退出，仅输出 stderr 诊断。macOS/Linux 执行这些 POSIX 测试；Windows 使用原来的直接 Node 启动配置。

`npm run test:host -- /path/to/codex` 使用实际 Codex app-server 的插件加载器，分别在两个隔离的 CODEX_HOME 安装仅启动命令不同的副本：绝对命令必须被拒绝，允许的裸命令必须发现工具、原生入口及真实 HTML 资源。使用合成 HOME、NVM 和数据库，不访问用户数据、不创建模型会话。CI 额外使用固定版本 `@openai/codex@0.162.1` 跑此回归；本机交付还用当前桌面捆绑 CLI 验证。原始 SDK 启动成功和 `plugin list` 中 installed/enabled 都不能代替这层验证。

## 原生自动认领

`test/integration/automation.test.ts` 与 `test/mcp/automation.test.ts` 使用真实 SQLite 和官方 MCP 客户端检查配置修订、未知结果恢复、自动认领门禁与持久会话绑定。`test/e2e/automation.spec.ts` 用模拟原生宿主连接同一真实服务，检查显式 `target:new, send:true` 配置请求、当前草稿保留、确认前 pending、暂停、只读核对、拒绝／传输失败及不支持的环境。测试客户端回报原生记录，不能作为实际宿主创建自动化或执行任务的证据。

0.4.1 的默认初始化回归使用每例独立数据库，检查自动启动不提供设置 UI、并发一次性初始化、周期只读刷新和错误不循环派发。任务讨论用已配置的模拟调度器隔离其原生草稿协议，防止默认初始化消息干扰断言。真实宿主自动化创建、项目绑定方式与首轮实际任务执行分别验收；创建成功不等于 worker 已完成任务。

## 平等同伴组织

worker-pool 集成覆盖固定容量共享目标、同伴 CLAIM/FAIL 传播、隔离 Git 元数据与未跟踪文件不复制、完成后停止／新目标复用、活跃回合及会话打开阶段的停止竞争。MCP 回归检查后台不暴露任务创建／资源定义修改、停止后的写入门禁、工具返回附加共享更新，以及完整历史字面查询。浏览器回归验证停止／恢复的版本检查和任务数不变。

显式真实模型检查 node scripts/verify-pool-runtime.mjs --live 与普通 CI 分开：三个真实模型会话对单个合成目标自行划分贡献、定向消息并交叉复核，根验收完成后验证自动停止；不修改业务看板或真实环境。具体结果与局限见 verification.md。

## 真实进程故障与有界持续测试

`npm run test:reliability` 执行真实 OS 进程故障测试及会话协议回归，普通 `npm run check` / CI 也包含这些测试。运行时子进程直接加载源码，使用隔离 SQLite 和可控执行替身，不启动模型、不读取真实看板、不连接开发机或生产。Windows 跳过 POSIX 信号故障组；当前 CI 在 Linux 执行，本机在 macOS 执行。

| 故障或竞争 | 可观察验收标准 |
| --- | --- |
| 执行前 SIGKILL | 保持 uncertain，不编造完成、不盲目重放 |
| 副作用提交后、turn/start 确认前或确认后 SIGKILL | 从独立执行台账核查完成，确认游标；不产生第二次执行，后续事件复用原 threadId |
| 三个独立运行时同时争抢，owner 被 SIGSTOP / SIGKILL | 存活 owner 不被抢占；死亡后由存活进程核查、接管并继续 |
| 外部执行仍 active、记录不可得或明确失败 | 保持 uncertain 或 error，禁止自动重试有部分副作用的失败回合；完成证据可得后显式核查恢复 |
| 审批暂停后崩溃、核查、恢复 | 暂停及原因保持，旧检查点不能抹掉人工状态；只有显式恢复才消费后续工作 |
| 人工停止／全部完成时三个回合仍在途 | 跨进程恢复后不被晚到消息唤醒；未核实回合仍显示 stopping，全部核实后才 stopped/completed |
| 多轮突发消息、广播 FACT/FAIL、分页和重复唤醒通知 | 逐个核对稳定事件 id 与接收者，无遗漏或重复；相同文本的不同事件必须保留；身份和工作目录不变，人类任务／资源数不增长 |
| 空闲恢复扫描 | 不调用执行替身，不因自己的文件通知形成高速扫描循环 |

测试中的外部台账与运行时状态库分离，不对执行尝试做唯一键去重，重复执行会直接增加计数并导致断言失败。受控进程在指定执行边界等待，父测试实际发送 SIGKILL 后重启，不能用预填 running/uncertain 状态替代。台账仅模拟支持结果查询的外部系统；真实模型、外部接口的幂等性和副作用须另验收。

默认持续序列为 5 轮；加大但仍有界的检查：

```sh
SWARMBOARD_FAULT_ROUNDS=30 npx vitest run test/integration/process-recovery.test.ts -t 'bounded fault sequence'
```

每轮强杀一个 owner，三个同伴处理 160 条定向消息与两条全员广播。输入固定，OS 进程调度真实；允许 3–100 轮，总测试超时 120 秒。30 轮通过代表该故障序列下的结果，不等于数小时／数天真实模型持续运行、网络分区或所有外部副作用恰好一次。

## 内部协作空闲恢复

`idle-recovery.test.ts` 使用隔离 SQLite、可控时钟和会话替身，检查十分钟边界、单个既有 peer 轮换提醒、两次预算、重启保留、普通消息不重置预算、目标修订重置、忙碌／停止／审批／未知执行／blocked／in_review／完成时不盲目唤醒，以及 4001 条无关历史跨页积压时先读完队列再计空闲。`process-recovery.test.ts` 在信号持久化后、看板追加前与追加后两个真实进程边界实际 SIGKILL，核对重启后仅一条信号和一次消费，原成员和 threadId 不变。它们不证明真实模型能自行解决所有阻塞。

浏览器回归分别检查成员数／执行数、真实空闲状态、下次检查时间、耗尽后的可见提醒及版本化重新检查。内部模型执行策略通过每轮固定提示和 skill 交付，不将行为约定描述为对恶意拥有 Shell 的客户端的强制隔离。
